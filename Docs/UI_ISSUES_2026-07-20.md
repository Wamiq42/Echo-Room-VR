### Cross-cutting red flag: negative X scale on every world-space panel

Both menu panels are placed with a **mirrored transform**:

- `VRLoadingScreen.cs:80` — `transform.localScale = new Vector3(-worldScale, worldScale, worldScale);`
  (repeated at `:241` and `:250`)
- `VRPauseMenu.cs:36` — `fixedStartMenuScale = new(-0.002f, 0.002f, 0.002f)`
- `VRPauseMenu.cs:553` — `transform.rotation = cameraTransform.rotation * Quaternion.Euler(0f, 180f, 0f);`
- `VRLoadingScreen.cs:249` — same 180° flip

The panel is rotated 180° so its **front face points away from the player**, then negative X scale
mirrors the visuals back so the text reads correctly. It looks right, but geometrically the player
is always looking at the **back face** of a mirrored panel.

This one hack plausibly explains **Issue 2** on its own, and it interacts with Issues 1 and 4. I
would treat unwinding it as the single highest-value fix in this list. It needs to be confirmed in
Play Mode before we commit to it — see Issue 2.

## Issue 1 — Menus render unstyled and stacked outside Play Mode

**Observed (Pic 1):** In the Scene/Game view outside Play Mode, every menu screen (main menu, pause,
settings, captured, loading) draws simultaneously as flat unstyled text rows. Wamiq wants the
Editor to show what the game shows — an authoring-convenience request, not a runtime bug.

**Root cause — three separate `Awake()`-only side effects:**

1. **Stylesheets are attached at runtime, not in the asset.**
   `VRLoadingScreen.cs:61-62`:
   ```csharp
   if (loadingStyles != null && !documentRoot.styleSheets.Contains(loadingStyles))
       documentRoot.styleSheets.Add(loadingStyles);
   ```
   Edit mode never runs `Awake()`, so no USS is applied → the completely unstyled look in Pic 1.

2. **Screens are hidden at runtime, not by default.**
   `VRLoadingScreen.cs:82` calls `HideImmediate()`, which sets `root.style.display = DisplayStyle.None`
   (`:233`). Until that runs, every screen in every document is visible → the stacking.

3. **Document layout is configured at runtime.**
   `VRLoadingScreen.cs:53-58` and `VRPauseMenu.cs:154-157` assign `visualTreeAsset`,
   `worldSpaceSizeMode`, `worldSpaceSize`, `pivot`, `position`, `sortingOrder` in code. The
   serialized inspector values differ, so edit-mode sizing is wrong even once styles apply.

**Options to discuss:**

- **A (recommended) — move authoring data into the assets.** Add `<Style src="..."/>` to each UXML,
  set `display: none` as the default in USS for non-active screens, and set the `UIDocument`
  inspector fields to match what `Awake()` assigns. Code then only *changes* state, never
  *establishes* it. Fixes the Editor view as a side effect and removes hidden runtime coupling.
- **B — `[ExecuteAlways]` on the UI scripts.** Smallest diff, but `Awake`/`Update` then run in the
  Editor, which risks scene-dirtying, `Camera.main` resolution in edit mode, and coroutine
  weirdness. I'd avoid it.
- **C — an Editor-only preview toggle.** Most control, most code to maintain. Only worth it if we
  want to preview individual states on demand.

**Open question:** do you want edit mode to show *one* representative screen (e.g. main menu), or
all screens correctly styled but hidden until selected? A affects the answer.

## Issue 2 — World-space UI does not respond to controller rays (mouse works)

**Observed (Pic 2):** Both rays visibly land on the menu; no hover, no click. Mouse in the Game view
works fine.

**How ray→UI input actually works here (important, and not what I first assumed):**

There is **no `GraphicRaycaster` or `TrackedDeviceGraphicRaycaster` anywhere** in either scene —
verified, zero hits. No uGUI canvas in this project is clickable. All pointer input flows through
UI Toolkit via this chain:

`XRRayInteractor` → `XRUIInputModule` → **`UIElements.PanelInputConfiguration`** →
`XRUIToolkitManager` + generated `BoxCollider` on the panel.

Confirmed *correct* — these are all ruled out:

- `EventSystem` has `XRUIInputModule` (`MainMenuScene.unity:1040`, `MainScene.unity:4034`) with
  `m_BypassUIToolkitEvents: 0` (`:1049`) — UI Toolkit events are forwarded
- `m_EnableUIInteraction: 1` on all four ray interactors (`MainMenuScene.unity:2206`, `:3981`)
- `m_RaycastTriggerInteraction: 1` (Collide) — the trigger collider *will* be hit
- `PanelInputConfiguration.m_ProcessWorldSpaceInput: 1`, `m_MaxInteractionDistance: Infinity`,
  `m_AutoCreatePanelComponents: 1` (`MainMenuScene.unity:1122-1131`)
- The `Main Menu` panel **does** have `XRUIToolkitManager` (`MainMenuScene.unity:2727`) and a
  `BoxCollider` of `900×560×4`, `isTrigger`
- Both UIDocument GameObjects are on layer 0 (Default)

**Two live hypotheses, in priority order:**

**H1 — `PanelInputConfiguration.m_InteractionLayers` drift between scenes.**
`MainMenuScene.unity:1122-1131` has `m_InteractionLayers.m_Bits: 4294967291` (all layers except
bit 2). `MainScene.unity:4113-4116` has **`1075`** — a much narrower mask. These are XRI
*interaction layers*, not physics layers, and they must intersect with the ray interactors'
interaction layer mask for the panel to receive events. This drift looks unintentional and is the
cheapest thing to check first. **Pic 2 is the main menu**, which has the permissive mask — so if
this were the whole story the main menu should work, meaning H1 alone probably doesn't explain
Pic 2. Check it anyway; it likely explains ray failures in `MainScene`.

**H2 — the mirrored / back-facing transform (see cross-cutting note above).**
The generated `BoxCollider` inherits the panel's negative X scale. Ray hits then convert to
mirrored panel-local coordinates, and the player is looking at the panel's back face. Either the
hit is rejected outright or it maps to a mirrored X so the pointer "hovers" empty space while the
ray visually sits on a button. Mouse input does not go through the world collider, so it is
unaffected — which matches the reported symptom exactly.

**H3 — zero-sized geometry on the frame of show.** `VRPauseMenu.cs:398-399` carries this comment:

> `// UI Toolkit world-space geometry is zero-sized on the frame a hidden screen is shown.`

and works around it with `EnableInputAfterLayout` (`:394-413`), deferring collider and pointer
enable by two frames. **`VRMainMenu` has no equivalent deferral.** If the main menu's collider is
generated while the panel is zero-sized and never regenerated, the collider stays degenerate and no
ray can ever hit it — while the visuals render fine. This would explain Pic 2 cleanly.

**Proposed verification, ~15 minutes in Play Mode, in this order:**

1. In Play Mode, select the `Main Menu` GameObject and inspect the `BoxCollider` size in the
   Inspector. If it is zero or tiny → **H3 confirmed**, port `EnableInputAfterLayout` to
   `VRMainMenu`. This is the fastest discriminator, do it first.
2. If the collider is correctly sized, enable gizmos and check whether the ray visibly terminates at
   the panel. If it passes through → H2.
3. Temporarily set panel scale positive and drop the 180° rotation; confirm rays start working (text
   will render mirrored — expected, fine for the test). If they do → H2 confirmed.
4. Reconcile `m_InteractionLayers` across both scenes regardless of outcome (H1).

**Do not** fix this by hand-authoring a `BoxCollider` plus a custom raycast handler — that's the
tempting shortcut and it would permanently fork us off the UI Toolkit input path.

## Issue 3 — Tutorial prompt is controller-attached instead of world-anchored

**Observed (Pic 3):** The "SONAR / Press the SONAR button to reveal the corridor" prompt tracks the
controller.

**Root cause — confirmed, unambiguous.** `TutorialDirector.cs:337-348`:

```csharp
void UpdatePromptPose()
{
    if (tutorialPromptCanvas == null || head == null || rightController == null) return;

    Transform prompt = tutorialPromptCanvas.transform;
    Vector3 offset = head.right   * PromptOffsetFromView.x +
                     head.up      * PromptOffsetFromView.y +
                     head.forward * PromptOffsetFromView.z;
    prompt.position = rightController.position + offset;      // ← line 345
    prompt.rotation = Quaternion.LookRotation(prompt.position - head.position, head.up);
    prompt.localScale = Vector3.one * PromptCanvasScale;
}
```

The canvas *is* `RenderMode.WorldSpace` (`:297`) — so your instinct was half right — but line 345
re-drives its position from `rightController.position` every time it's shown, so it behaves as if
it were controller-parented. `PromptCanvasScale = 0.0005f` (`:137`).

**Design question this raises (worth deciding before fixing):** the prompt is currently anchored to
the controller *deliberately* — it's a "look at your hand" instruction. Three different behaviours
are defensible:

- **Fixed world anchor.** Placed by the tutorial author at a spot in the corridor. Best for
  readability and screenshots; risks the player turning away and losing the instruction entirely.
- **Head-relative, world-locked on show.** Placed once in front of the player when it appears, then
  frozen. Comfortable, always initially visible, doesn't chase the player. **My recommendation** —
  it matches how the pause menu already behaves (`VRPauseMenu.cs:541`).
- **Keep controller-attached but stabilise it.** If the intent really is "read this off your hand",
  the fix is damping/smoothing rather than re-anchoring.

Also noted while reading this file: `TutorialDirector.cs:515-528` (`CreateFadeOverlay`) builds the
ending fade as `RenderMode.ScreenSpaceCamera` with `planeDistance` at the near clip plane. In VR
that renders at a fixed screen depth and is a known comfort/stereo problem. Not on your list —
flagging it for the same work package.

## Issue 4 — Menus intersect walls

**Observed (Pic 4):** The pause menu clips into the brick wall.

**Important:** wall avoidance already exists — this is a *tuning/coverage* bug, not a missing
feature. `VRPauseMenu.cs:547-553`:

```csharp
float placementDistance = distanceFromCamera;
if (keepInFrontOfWalls && Physics.Raycast(cameraTransform.position, cameraTransform.forward,
        out RaycastHit hit, distanceFromCamera, wallMask, QueryTriggerInteraction.Ignore))
    placementDistance = Mathf.Max(minimumDistanceFromCamera, hit.distance - wallPadding);
```

Defaults: `distanceFromCamera = 2.1f` (`:31`), `wallPadding = 0.15f` (`:38`),
`minimumDistanceFromCamera = 0.45f` (`:39`), `wallMask = ~0` (`:40`).

**Three concrete defects in that logic:**

1. **Single centre ray, wide panel.** At `worldSpaceSize` 900×560 and 0.002 scale the panel is
   ~1.8 m × 1.12 m. One ray down the view centre says "clear" whenever the wall is off to the side,
   so the panel's *corners* punch through — exactly what Pic 4 shows. Needs corner/multi-point
   probing (5 rays: centre + 4 corners, take the minimum) or a `Physics.BoxCast` sized to the panel.
2. **`wallMask = ~0` hits everything.** Props, the player's own colliders, trigger volumes, and
   interactables can all shorten the placement distance, causing the menu to snap uncomfortably
   close for no visible reason. Should be an explicit geometry layer.
3. **Only runs on the dynamic path.** `ShouldUseFixedWorldPlacement()` (`:528-533`) routes the Start
   and Start→Settings states to `PlaceMenuAtFixedWorldAnchor()` (`:535-539`), which does no wall
   check at all. `VRLoadingScreen.cs:238-243` has the same unguarded fixed-placement path with
   `useFixedWorldPlacement = true` by default (`:16`).

**Options to discuss:**

- **A (recommended) — `BoxCast` sized to the panel + a dedicated `MenuOcclusion` layer mask,**
  applied on both the dynamic and fixed paths, with the fixed anchor treated as a preferred
  position that gets pulled in when blocked.
- **B — shrink the panel and reduce `distanceFromCamera`.** Cheapest, reduces frequency, doesn't
  fix the class of bug. Fine as an interim if we're time-boxed.
- **C — depth-test-off / always-on-top rendering.** Guarantees legibility but the menu floats
  *through* walls, which reads as broken in VR and hurts depth perception badly. I'd rule this out.
- **D — fade the menu out when occluded and re-place it.** Best-feeling in commercial VR titles,
  most work. Worth considering if menus are frequently opened mid-corridor.

**Open question:** should the pause menu be world-anchored where it first opened (current dynamic
behaviour), or should it follow the player if they walk away? That changes whether occlusion is a
one-shot placement check or a per-frame concern.

## Issue 5 — Loading screen does not block input or suppress other UI

**Observed (Pic 5):** During "TUNING SIGNAL / RETURNING TO MAIN MENU", the pause menu is still
visible behind the loading panel and rays/input remain live.

**Root cause — confirmed by absence, and it's a caller problem, not a loading-screen problem.**

`VRLoadingScreen.cs` (all 258 lines) contains **no** input gating and **no** suppression of other
documents. `ShowLoading()` (`:98-107`) only sets its own `display` and progress. It has no
`BoxCollider` and no `XRUIToolkitManager` (component lists at `MainMenuScene.unity:2508-2511`,
`MainScene.unity:7900-7903`) — so it is deliberately non-interactive, which is correct. It just
doesn't stop anything *else* from being interactive.

Input suppression is left to the callers, and it's handled **inconsistently in three places**:

1. **`VRMainMenu.SetControllerPointersVisible()` (`:262-268`)** does suppress pointers — but by
   scanning every `Transform` in the scene and matching a **literal string**:
   ```csharp
   if (transforms[i] != null && transforms[i].name == "Menu UI Ray")
       transforms[i].gameObject.SetActive(value);
   ```
   Called with `false` before scene loads (`:216` `BeginGameplay`, `:199` `StartTutorial`).
   Renaming that GameObject silently breaks pointer suppression, and the full-scene scan is
   wasteful. Fragile, but it does work today.

2. **`VRPauseMenu`** does it properly via the serialized `vrPointerRoots` array (`:24`, toggled at
   `:456-462`, wired in `MainScene.unity:9842-9844`), plus `PauseTime()` (`:464-470`) and
   `AudioListener` pause (`:479-485`).

3. **`GameManager.cs`** — the path in Pic 5. It guards re-entrancy with `_isTransitioning` (`:32`)
   and calls `LoadSceneRoutine` / `ShowThankYouThenLoad` / `CoverPrefabSwap`, but it **never
   disables interactors and never hides the pause menu**. That is the actual gap producing Pic 5:
   Return To Menu goes through `GameManager`, so neither suppression mechanism above fires.

The loading screen already exposes the state we need: `IsBusy` (`:38`) is true for the whole load,
and `sortingOrder = 1000f` (`:58`) draws it over the menus (`:100` on both menu scripts). Only the
*input and sibling-UI* half was never wired.

**Options to discuss:**

- **A (recommended) — a single `UIStateManager` / modal-stack owner.** One component decides which
  UI layer owns input; everything else asks it. This is now clearly the right call: we already have
  *three* competing suppression mechanisms (string-matching scan, serialized array, and nothing at
  all), and Pic 5 is exactly what happens when a fourth code path forgets to participate. Also lets
  us delete the `"Menu UI Ray"` string match.
- **B — mirror the pause menu's approach inside `VRLoadingScreen`.** Add `vrPointerRoots`, disable
  pointers and hide the pause menu on show, restore on hide. Fast and low risk, but adds a *fourth*
  ownership implementation. Acceptable only as a stopgap.
- **C — have `GameManager` disable pointers around its transitions.** Smallest possible change and
  it does fix Pic 5 specifically, since `GameManager` is the path that's missing it. Doesn't
  address the underlying duplication.

**Note:** whichever we pick, the loading screen must use **unscaled** time throughout — it already
does (`Time.unscaledDeltaTime` at `:88`, `Time.realtimeSinceStartup` at `:132`), so pausing time
during load is safe.

## Issue 7 — Panel resolution and apparent size

**Observed:** "All panels' size is small, it should be 1920×1080."

These are **two different problems** and it's worth separating them before we change numbers.

**Current values:**

| Setting | Value | Where |
| --- | --- | --- |
| `worldSpaceSize` | 900 × 560 | `VRMainMenu.cs:56`, `VRPauseMenu.cs:155`, `VRLoadingScreen.cs:55` |
| `worldScale` | 0.0016 (menus) / 0.002 (pause fixed) | `VRMainMenu.cs:20`, `VRPauseMenu.cs:36` |
| `PanelSettings` reference resolution | 1200 × 800 | `VRMenuPanelSettings.asset` |
| **Resulting physical size** | **1.44 m × 0.90 m** | 900 × 0.0016 |

**7a — Authoring resolution (your 1920×1080 request).** This is a legitimate ask. `worldSpaceSize`
is the panel's virtual-pixel buffer, so it directly determines texel density — more pixels means
crisper text in the headset, which matters a lot in VR. **But it is not a one-number change:**

- Aspect ratio shifts from 1.607:1 (900×560) to 1.778:1 (16:9). **Every UXML/USS layout will
  reflow.** That's a real pass over `VRMenu.uxml`, `VRMenu.uss`, `VRLoadingScreen.uxml/.uss`.
- To keep the same physical size, `worldScale` must drop to `1.44 / 1920 = 0.00075`. If we change
  resolution without this, panels become 3.07 m wide — enormous at 2.1 m away.
- `PanelSettings` reference resolution (1200×800) should be updated to match, or it'll fight the
  layout.
- Cost: more GPU memory and fill for the panel buffer. On Quest that's worth checking, though at
  these sizes it should be fine.

**7b — "Panels feel small" is a *distance* problem, not a resolution problem.** See Issue 9. A
1920×1080 panel at the same distance and physical scale looks **exactly the same size** — just
sharper. If the complaint is "I have to squint / it's far away," raising the resolution alone will
not fix it.

**Recommendation:** do 7b first (cheap, immediately felt), then decide on 7a as a separate,
deliberate reflow pass. Don't bundle them — if we change resolution and distance at once and it
feels wrong, we won't know which change caused it.

## Issue 8 — Loading screen appears *after* the maze has already loaded ⚠️ highest severity

**Observed (Batch 2, Pics 1, 3, 4):** Press Play → the maze loads and becomes visible → *then* the
"TUNING SIGNAL / ENTERING MAZE A" panel appears, drawn over maze geometry. Pic 4's Scene view shows
it overlapping a "LEVEL 1 / Find the exit." banner.

**Root cause — confirmed. The loading screen is scene-local, so it cannot survive the transition it
exists to cover.**

Neither `GameManager` nor `VRLoadingScreen` is `DontDestroyOnLoad` (the only three in the project
are `AOPlaytestLogger.cs:93`, `EchoMusicManager.cs:32`, `TutorialRuntimeObserver.cs:34`).
`GameManager` is a singleton (`GameManager.cs:36, 48-61`) but a **scene-local** one — the new
scene's instance replaces the old. It resolves its loading screen with a scene-local lookup
(`GameManager.cs:60`):

```csharp
if (loadingScreen == null) loadingScreen = FindObjectOfType<VRLoadingScreen>(true);
```

There are **two separate `VR Loading Screen` objects**, one per scene:
`MainMenuScene.unity:2515` and `MainScene.unity:7907`.

**The actual sequence:**

1. `VRMainMenu` starts `LoadSceneRoutine("MainScene")` — the coroutine runs *on the MainMenuScene
   loading screen object*.
2. It correctly holds `allowSceneActivation = false` and shows progress (`VRLoadingScreen.cs:143-150`).
3. `allowSceneActivation = true` (`:154`) → `MainScene` loads `Single` → **MainMenuScene unloads and
   that loading screen GameObject is destroyed mid-coroutine.** The cover disappears at the exact
   moment it's needed.
4. `MainScene`'s own `GameManager.Start()` runs and does its prefab swap through
   `CoverPrefabSwap(...)` using **MainScene's** loading screen — which is why you see "TUNING SIGNAL /
   ENTERING MAZE A" *inside* the maze, after arrival.

**Three aggravating factors found while tracing this:**

**(a) The screen fade is explicitly cleared right before the loading screen shows.**
`GameManager.cs:98`, inside `InitializeGame()`:
```csharp
if (screenFade != null) screenFade.SetOpacity(0f);   // screen made FULLY CLEAR
if (loadingScreen != null)
    yield return loadingScreen.CoverPrefabSwap("ENTERING " + ..., () => LoadLevel(levelIndex));
```
So the one thing that *could* have masked the gap is deliberately switched off one line before the
gap occurs. Easy win — inverting these two lines alone would visibly improve things.

**(b) Total loading UI is ~10 seconds, split across the scene boundary.** 5 s `minimumDisplayTime`
on the menu side (`MainMenuScene.unity:2510`) plus another `Mathf.Max(5f, minimumDisplayTime)` in
`CoverPrefabSwap` (`VRLoadingScreen.cs:219-221`). Separately worth tuning down.

**(c) The MainScene loading panel is anchored to a main-menu coordinate.**
`MainScene.unity:7930-7932` — `useFixedWorldPlacement: 1`, `fixedWorldPosition: (-3.04, 0.95, -1.342)`,
the *same* hallway coordinate the main menu uses. But `CoverPrefabSwap` runs `MovePlayerToSpawn`
(`GameManager.cs:173`) while the panel is up, and `PlaceInFrontOfPlayer()` early-returns on the
fixed branch (`VRLoadingScreen.cs:238-243`) and never re-faces the camera. **So after the teleport
the panel can be beside or behind the player** — which is what the odd framing in Pic 4 is showing.

**The overlapping banner** is a fourth actor. `MazeWorldTextController.cs:22-27` starts its 5-second
"LEVEL 1 / Find the exit." intro from `OnEnable()` — which fires the instant `LoadLevel()`
instantiates the maze prefab, i.e. *inside* `CoverPrefabSwap` with ~5 s of hold still to run. It's a
legacy `TextMesh` living inside each maze prefab (e.g. `Maze_5x5_A.prefab:2451-2460`), not part of
the UI Toolkit stack, so it doesn't sort against anything.

**Consequence worth calling out separately: the player never sees the level intro.** Its entire 5 s
life is consumed behind the loading screen. That banner has effectively never worked in play.

**Options to discuss:**

- **A (recommended) — make the transition layer persistent.** A `DontDestroyOnLoad` bootstrap object
  owning the loading screen, screen fade, and transition state. It shows *before* the load starts,
  survives the scene swap, and hides only once the destination has finished its own setup (prefab
  swap, lighting init, level spawn). This is the only option that actually gives you the sequence
  you described: cover in the main menu → hold → reveal the maze.
- **B — fade to black before loading, fade in after.** `VRScreenFade` already exists
  (`GameManager.cs:58-59`). Cheaper than A and hides the seam, but the *progress bar* still can't
  span the transition, so "TUNING SIGNAL" would become decorative rather than informative.
- **C — additive scene loading.** Keep a persistent bootstrap scene, load/unload maze scenes
  additively. Cleanest long-term architecture and solves this whole class of problem, but the
  largest change and it touches lighting/lightmap init (`PrefabLightmapRuntime.InitializeSceneLighting()`,
  `GameManager.cs:57`).

**Also needs deciding:** `MazeWorldTextController`'s intro must be gated on "transition complete"
rather than `OnEnable`, whichever option we pick. And you asked for "a small delay then the level
loads" — that's `minimumDisplayTime` (`VRLoadingScreen.cs:19`, currently 5s), which already exists
and works; it just can't currently span the scene boundary.

**My honest read:** this is the most structurally serious item in either batch. Issues 5 and 6 are
symptoms of the same missing concept — nothing owns "we are transitioning." I'd fix this before the
cosmetic items.

## Issue 9 — Main menu: no locomotion, and the menu sits too far away

**Observed (Batch 2, Pic 2):** Can't move around in the main menu scene; the menu is small and distant.

**Current placement:** `VRMainMenu.cs:21-23` — `useFixedWorldPlacement = true`,
`fixedWorldPosition = (-3.04, 0.95, -1.342)`, with `distanceFromCamera = 2.1f` (`:18`) used only on
the non-fixed path. Panel is 1.44 m wide (see Issue 7).

**Two decisions for you, and they interact:**

**9a — Locomotion in the main menu.** **Confirmed: movement is deliberately disabled**, not merely
absent. The XR Origin prefab is instanced in `MainMenuScene.unity` with a large block of
`m_Enabled: 0` prefab overrides — `LocomotionMediator` (`:1707-1718`), `XRBodyTransformer`
(`:1719-1734`), the move provider (`:520-526`, override at `:4931-4934`), and
`UnifiedLocomotionBridge` (`:5148-5161`). `MainScene.unity:16766-16768` has the same bridge enabled
for gameplay.

So re-enabling means **undoing a deliberate decision** — someone turned this off on purpose. Worth
finding out why before reversing it (my guess: to stop players wandering off the lit set, or out of
the panel's fixed-anchor sightline). Decide *why* you want it first:

- If it's **"the menu room should feel like a real place"** → enable locomotion, and then the menu
  must stop using a hard-coded world position, because the player can walk away from or behind it.
  It'd need to be either player-relative-on-open or genuinely diegetic (a physical panel in the room
  you walk up to — which honestly suits Echo Room's fiction well).
- If it's **"I just want to adjust my viewing position"** → a recenter/height option is safer and
  avoids the player wandering out of the lit area.

**9b — Menu distance.** Straightforward: it's a serialized position, easy to tune. Standard VR
comfort range for a readable menu panel is **1.2–2.0 m**; text below ~1 m causes eye strain from
vergence. Recommend measuring the actual current camera→panel distance in the scene and pulling it
to ~1.5 m, or switching the main menu to the same dynamic placement the pause menu uses
(`distanceFromCamera = 2.1f`, probably tune to ~1.6).

**Caution:** if we enable locomotion (9a) *and* keep the fixed world anchor, we've built a menu the
player can walk behind — combined with the back-facing panel problem in Issue 2, that will be
genuinely confusing. Decide 9a before touching 9b.

## Issue 10 — No visible countdown, then sudden "TIME EXPIRED"

**Observed (Batch 2, Pic 5):** Failure screen fires with no prior indication that a timer existed.

**Root cause — the timer exists and is deliberately hidden. This is a discoverability problem, not a
missing feature.** `Assets/_EchoRoom/Scripts/Managers/MazeLevelTimer.cs`:

- Time limit: **180 s per maze** for A/B/C/D (`:14-17`)
- Display is a `TextMeshPro` parented to the **right controller** (`:257-259`), scale 0.035 (`:22`)
- Hidden by default — `SetDisplayAlpha(0f)` in `Awake()` (`:59`)
- Revealed for **3 seconds** (`:25`) only on **A button / gamepad South / keyboard T** (`:298-305`)
- Flashes 4 times at level start (`:33-36`, `FlashAtLevelStart()` `:206-221`) — the only unprompted warning
- Scene values confirmed all `180` (`MainScene.unity:13103-13106`); component sits on the XR Origin (`:13092-13102`)
- Failure path: `ExpireTimer()` (`:193`) → `VRPauseMenu.cs:261` `SetFailureCopy("TIME EXPIRED", ...)`

**The killer detail:** that 4-flash start warning fires **while the loading screen is still covering
the view** (see Issue 8 — `CoverPrefabSwap` holds for ~5 s after the level instantiates). So the
player misses the *only* unprompted signal that a timer exists. It isn't that the warning is subtle
— in practice it is never seen at all.

So it's a "check your watch" design where the watch was never introduced. The intent is good and
fits a game about limited information, but as shipped a first-time player gets a hint they cannot
see, on a controller they aren't looking at, then loses 3 minutes later with no warning. **That's
not a fair fail state.** Note this partly self-corrects once Issue 8 is fixed — another reason to
sequence Issue 8 first.

**Also found:** `GetDuration` returns `-1f` for any level it can't name-match (`:168-176`), so
**Maze E has no time limit at all** and `StopTimer()` is called (`:152-156`). Intentional, or an
oversight from the name-matching? Worth confirming.

**Options to discuss:**

- **A (recommended) — keep the hidden-by-default design, add escalating unprompted warnings.**
  Auto-reveal at 60 s / 30 s / 10 s, and add audio (a heartbeat or a signal-decay cue fits the
  fiction better than a beep). Preserves the design intent, removes the unfairness.
- **B — persistent HUD timer.** Always visible. Fair and clear, but flatly contradicts the game's
  "play blind, see with sound" premise. I'd resist this one.
- **C — teach the reveal button in the tutorial.** Necessary regardless of A or B — right now
  nothing tells the player the timer exists. `TutorialDirector` already has a prompt slot pattern
  for exactly this.
- **D — reconsider whether a hard 180 s fail belongs in a first maze at all.** Worth asking. A
  timer that only appears in later mazes, or a soft fail (the entity closes in) rather than a hard
  reset, may serve the game better.

**Also note:** `MazeLevelTimer.ResolveTrackingTargets()` (`:273-285`) finds the controller by the
literal string `"Right Controller"` — the **third** name-string lookup in this codebase
(alongside `VRMainMenu.cs:262-268` and the tutorial prompt). Worth fixing together.

## Issue 13 — Loading screen visible in Scene view but not Game view

Game view at the same moment shows only the "TIME EXPIRED" menu. The loading screen is running but

**Root cause — confirmed, and it's Issue 8(c) reproducing exactly as predicted.** This is not a
culling or rendering bug. The panel is rendering fine; it's rendering **somewhere else in the
world.**

`MainScene.unity:7930-7932`:
```yaml
useFixedWorldPlacement: 1
fixedWorldPosition: {x: -3.04, y: 0.95, z: -1.342}
fixedWorldEulerAngles: {x: 0, y: 89.752, z: 0}
```

That coordinate is the **main-menu hallway anchor** — the identical value hard-coded in
`VRMainMenu.cs:22`, `VRPauseMenu.cs:34`, and `VRLoadingScreen.cs:17`. Meanwhile
`GameManager.LoadLevel()` calls `MovePlayerToSpawn(ResolveSpawnPoint(...))` (`:173`), teleporting

(`VRLoadingScreen.cs:238-243`), so the panel never follows.

Result: the player is in the maze, the loading panel is back at the hallway coordinate. The Scene
view camera happens to be positioned where it can see it; the game camera cannot.

**This also explains an earlier observation.** In Batch 1 Pic 5 you *did* see the loading panel — you
happened to be standing near that hallway coordinate at the time. Whether the loading screen is
visible at all is currently a matter of **where the player happens to be standing.**

we do for Issue 8, that magic number needs to become a single owned anchor — or better, the loading

## Issue 14 — Wrist-mounted objective + timer display (feature request)

**Requested:** a small menu on one controller showing the timer and the current objective — "Find a
way out", "Find 3 switches", "Interact with switches".

**My honest reaction: this is the right answer, and it resolves my Issue 12 pushback.** I argued
against a conventional HUD because a floating overlay is useless in a dark corridor and spends the
"play blind" premise. A wrist device the player physically raises is *diegetic* — it costs nothing
when you're not looking at it, it fits a survivor in a research facility, and checking it becomes a
deliberate act with a small time cost. That's a mechanic, not a HUD. I'd build this instead of the
Issue 12 HUD, not in addition to it.

**It also has precedent in the codebase.** `MazeLevelTimer` already does exactly this: a
`TextMeshPro` parented to the right controller (`:257-259`), scale 0.035, revealed on button press
(`:298-305`). Issue 14 is best understood as **generalising the existing timer display into a proper
wrist panel**, not building something new. That's a much smaller job than it sounds.

**Design decisions to settle before building:**

1. **Which hand?** The timer currently lives on the **right** controller and reveals on the **right**
   A button. Sonar/ping is also right-hand. Moving the wrist panel to the **left** hand would avoid
   competing with the primary interaction hand and reads more naturally as "check your watch." My
   recommendation: left wrist, and move the timer there with it.
2. **Raise-to-view or button-to-reveal?** Button is what exists today. **Raise-to-view** — the panel
   fades in when you rotate your wrist toward your face — is dramatically more immersive and needs
   no button. It's a dot-product check against the head transform; genuinely not much code. Strong
   recommendation.
3. **Always-on while raised, or timed reveal?** The current 3 s timeout would be wrong for a panel
   you're deliberately holding up. Should stay visible while the raise gesture holds.
4. **How much does it show?** Timer + one objective line is the tight version. Objective + sub-progress
   ("2 of 3 switches") is richer but needs the data in point 5.

**Data availability — surveyed. Mixed, and the gap is narrower than expected.**

| What the panel would show | Status | Notes |
| --- | --- | --- |
| Remaining time | ✅ Free | `MazeLevelTimer.RemainingSeconds` / `IsRunning` (`:52-53`) |
| Level name + description | ✅ Free | via `GameManager.OnLevelLoaded(Level)` (`:45`) |
| Puzzle solved / unsolved | ✅ Free | `PuzzleBase.IsSolved` + `OnPuzzleSolved` (`PuzzleBase.cs:7, 10`) |
| Timer as a 0–1 fill ratio | ⚠️ Needs accessor | No `TotalSeconds` property exists |
| "2 of 3 switches" | ⚠️ Needs accessor | Computed privately, see below |
| Ping cooldown | ⚠️ Needs accessor | **Correction, see below** |
| "Level 2 of 5" | ⚠️ Needs accessor | `_currentLevelIndex` is private (`GameManager.cs:29`) |
| **Player-facing objective text** | ❌ Needs authoring | See below |
| **Multi-step objectives** | ❌ Needs new concept | See below |

> **Correction to something I told you earlier.** I said `PingEmitter` "already computes and returns
> `remainingCooldown`, nothing consumes it." **That was wrong.** `remainingCooldown` is a *local
> variable* inside the private method `TryEmitFromExternal()`. `PingEmitter`'s actual public surface
> is `LastPingInputSource`, the static `RequestPing`/`PlayPingSound` delegates, and
> `OnPingEmitted` — **no cooldown property at all.** The only way to read cooldown today is calling
> `RequestPing`, which *fires a ping* as a side effect, so a HUD cannot poll it. It needs a new
> read-only accessor. Cooldown is cheap to expose, but it is not free as I implied.

**The sub-progress data exists and is already computed — just not exposed.**
`EchoPuzzleController.cs` (the only `PuzzleBase` subclass) holds `_hitCount` (`:9`) and
`_targets.Count` (`:7`) and even logs `Progress: {_hitCount}/{_targets.Count}` at `:53` and `:78`.
That is literally "2 of 3." It needs a public accessor and nothing more.

**And it's already communicated diegetically.** `DoorProgressIndicators.cs` reads the same per-switch
state (`:6, 14, 51`) and drives three emissive indicators on the door. So the player is *already*
being told "2 of 3" by lights on the door. That's a good, on-theme solution that predates this
request. **Implication worth weighing:** a wrist readout repeating it is redundant and weakens the
diegetic version. The wrist panel may be more valuable for *what to do* than *how far along you are*.

**The real gaps:**

1. **Objective text.** `PuzzleBase` exposes only `IsSolved`, `OnPuzzleSolved`, `ResetPuzzle` — no
   name, description, or type. Nothing can label a puzzle generically. `Level.description` is
   boilerplate (identical on 4 of 5 levels). Strings must be written.
2. **Multi-step objectives.** "Find 3 switches" → "Find the exit" is a *phase* concept that doesn't
   exist outside the hardcoded tutorial `Step` enum (`TutorialDirector.cs:122`). Worse,
   `LevelExitTrigger` (`:22, 36, 46`) never announces when the exit becomes available — it just
   polls `IsSolved`. So the transition you described has **no signal to hang on** without adding one.
   This is the single biggest piece of new work in Issue 14, and it's easy to under-scope.

`Level.description` exists (`LevelData.cs:29`) and is populated — but with developer-facing text,
identical across four levels (`LevelData.asset:22, 29, 36, 43`):

> "Complete the puzzle and pass through the exit checkpoint to load…"

Usable as a *field*, not as *content*. Whichever way we go, the player-facing strings have to be
written.

**Recommended shape:** add a small `ObjectiveText` (and optional `RequiredCount`/`CurrentCount`) to
`PuzzleBase`, so objectives live next to the puzzle that defines them and stay in sync when a level
is edited. Fall back to `Level.description` only when a puzzle doesn't supply one. Avoid a separate
per-level objective table — that's the arrangement that drifts.

**One caution.** If objectives are authored as free text per level, they will drift out of sync with
the actual puzzles the moment a level is edited — the "LEVEL 1 / Find the exit." banner is already
an example of level-coupled text nobody has looked at in a while (and which, per Issue 8, has never
been visible in play). Prefer deriving objective text from puzzle state where the data supports it,
and treat hand-authored strings as the fallback rather than the default.

**Two implementation cautions found during the survey:**

- **It will collide with the existing timer display.** `MazeLevelTimer.EnsureDisplay()` (`:252-271`)
  already creates and owns a `TextMeshPro` parented to `"Right Controller"`, positioned in
  `LateUpdate` (`:126-137`), with its own reveal input. A new wrist panel must **absorb or replace**
  that display, not sit beside it — otherwise there are two competing wrist readouts with different
  reveal rules.
- **`EchoPuzzleController` recounts its targets every frame.** `RefreshTargets()` (`:98`) runs
  `GetComponentsInChildren` from `Update()` (`:20`), and prefers buttons over levers when both
  exist (`:107-113`). A HUD must read the controller's own cached values rather than counting
  independently, or the displayed total can disagree with the puzzle's. (The per-frame
  `GetComponentsInChildren` is also a performance smell worth a separate look on Quest.)

**Sequencing:** depends on nothing structural, but it should come *after* Issue 8, because right now
you cannot reliably observe level start to test it. Scope honestly: the panel and timer are small;
the **objective/phase model is the real work**, and it's a design task as much as a coding one.
